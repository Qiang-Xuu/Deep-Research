# xq-perf: 性能调优分析

输入一个性能现象，输出系统化的根因排查路径和优化方向。

## 核心原则

性能问题不是猜出来的，是证出来的。每个结论必须有数据支撑，每个假设必须有验证方法。

## 输入

用户描述的性能现象。可以是：
- 延迟抖动 / 长尾延迟
- 吞吐量瓶颈 / QPS 上不去
- CPU / 内存 / IO / 网络资源争抢
- Cache miss 飙升 / TLB miss
- 系统卡顿 / 偶发挂起
- 任何"感觉不对劲"的性能表现

## 执行流程

### 1. 症状定锚

把用户描述的模糊感受转化为可观测的分类：

| 类型 | 典型症状 |
|------|----------|
| 延迟型 | 响应时间忽高忽低、长尾延迟、P99 暴涨 |
| 吞吐型 | QPS/TPS 上不去、吞吐量随并发不线性增长 |
| 资源型 | CPU 打满、内存泄漏、磁盘 IO _wait 高、网络带宽耗尽 |
| 稳定性型 | 偶发卡顿、周期性抖动、负载不均、雪崩 |

**关键问题**：
- 这个现象是"突然出现的"还是"慢慢变坏的"？
- 有没有一个可复现的触发条件（特定请求、特定时间、特定负载）？
- 改了什么之后出现的？（代码、配置、硬件、流量）

### 2. 假设树生成

基于症状，自上而下生成可能根因的层级假设树：

```
系统层 ──→ 配置问题？调度策略？内核参数？
  │
服务层 ──→ 架构瓶颈？单点？依赖超时级联？
  │
进程层 ──→ 锁竞争？线程池耗尽？GC 压力？
  │
内核层 ──→ 上下文切换？中断亲和性？缺页？
  │
硬件层 ──→ NUMA 远端访问？PCIe 带宽？缓存一致性？
```

每个节点必须是一个**可证伪的陈述**，不是模糊猜测。

### 3. 验证实验设计

对每个假设，设计验证方法：

| 维度 | 内容 |
|------|------|
| 工具 | 用什么工具观测？（perf, bpftrace, eBPF, ftrace, vmstat, iostat, mpstat...） |
| 指标 | 看什么指标？阈值是多少？ |
| 预期 | 如果假设成立，数据应该长什么样？ |
| 成本 | 这个验证实验对线上系统的影响有多大？ |

**工具箱（选用）**：
- `perf` — CPU 热点、cache miss、分支预测
- `bpftrace` / `eBPF` — 动态追踪，零开销或低开销
- `ftrace` — 内核函数调用链
- `vmstat` / `iostat` / `mpstat` — 系统级资源概览
- `strace` / `ltrace` — 系统调用/库调用追踪
- `numactl --hardware` — NUMA 拓扑
- `lspci -vv` — PCIe 设备带宽和状态

### 4. 排查路径

按**验证成本从低到高**排列实验顺序：

1. 先看指标 dashboard（成本≈0）
2. 再看系统级统计（vmstat/iostat，成本≈0）
3. 然后针对性采样（perf top/record，成本≈低）
4. 最后动态追踪（eBPF/bpftrace，成本=中，需评估线上影响）

**绝不先做高成本实验**。如果一个假设可以通过看日志排除，不要用 eBPF。

### 5. 根因确认

哪个假设被数据证实？给出：
- 关键数据点（具体数字、对比基准）
- 证据链（从症状到根因的推理路径）
- 排除其他假设的理由

如果多个假设部分成立，说明**根因是复合的**。列出主次关系。

### 6. 优化方向

针对确认的根因，给出具体优化策略，按**实施成本从低到高**排列：

| 策略类型 | 例子 |
|----------|------|
| 配置调优 | 内核参数、线程池大小、GC 策略、NUMA 绑定 |
| 算法改进 | 减少锁粒度、批量处理、预取、无锁数据结构 |
| 架构调整 | 拆分瓶颈服务、异步化、缓存层、负载均衡 |
| 硬件升级 | 更多内存、更快 SSD、RDMA 网卡、更多 NUMA 节点 |

每个优化建议必须附带：
- 预期收益（量化，如"延迟降低 30%"）
- 潜在风险（副作用、回滚策略）
- 验证方法（怎么确认优化生效了？）

### 7. 写入 org 文件

整合分析过程为 org-mode 文档：

```org
#+title: 性能分析：{场景描述}
#+filetags: :perf:
#+date: [YYYY-MM-DD]

* 症状定锚
* 假设树
** 假设1：...
** 假设2：...
* 验证实验
* 根因确认
* 优化方向
** 配置调优
** 算法/架构
* 验证计划
```

写入 `~/Documents/notes/{timestamp}--perf-{场景}__perf.org`

## 红线

1. **不猜根因** — 每个根因必须有数据支撑
2. **不堆工具** — 用最便宜的工具排除最多假设
3. **不忽略边界** — 优化建议必须说明"在什么条件下生效"
4. **诚实标注** — 信息不足时直接说"这一步需要更多数据"，不硬撑
