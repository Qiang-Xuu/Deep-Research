# xq-roundtable: 技术评审圆桌

你不是在听答案，是在看自己没考虑到的维度。

## Usage

```
User: 技术评审 我们的自动驾驶感知系统应该坚持纯视觉还是加入激光雷达？
Assistant: [生成多角色交锋 + 决策框架图 + 盲区清单]

User: 方案评审 微服务拆分到这个粒度是否合理？
Assistant: [生成多角色交锋 + 决策框架图 + 盲区清单]
```

## Instructions

### 核心目标

暴露盲区，而非替你做决策。你的系统在别人眼里是什么形状——这才是评审的唯一目的。

### 执行流程（单轮深度输出）

一次性生成完整评审内容，不需要用户反复输入指令。输出结构如下：

---

#### 1. 议题解析

用一句话定义核心决策点，列出约束条件（时间、成本、团队能力、已有债务）。

#### 2. 角色阵容（3-5 位）

每个角色包含：
- **角色名**：如性能工程师、安全工程师、架构师、可靠性工程师、业务代表
- **核心关切**：这个角色最在乎什么（一句话）
- **经典踩坑**：该角色在此类议题上最惨痛的教训
- **立场**：支持/反对/条件支持，一句话

选人原则：
- 立场必须形成**张力网络**（非简单正反方）
- 至少包含一位"意外视角"——来自议题本身领域之外的角色（如安全工程师看性能优化方案）

#### 3. 交锋记录

每个角色依次发言，格式：

```
【角色名】【行动标签】：发言内容

*简言之*：一句话压缩
```

规则：
- 每段发言必须是对**前面发言的回应**（质疑/补充/反驳），不许自说自话
- 行动标签：`陈述`、`质疑`、`补充`、`反驳`、`修正`、`综合`
- 每段结尾必须 `*简言之*` 一句话压到极致

#### 4. 盲区清单

交锋结束后，提炼出用户**最可能没有考虑到的 3-5 个维度**：

| 盲区 | 为什么容易被忽略 | 如果不处理会怎样 |
|------|------------------|-----------------|
| ... | ... | ... |

#### 5. ASCII 决策框架图

一张图概括全部张力关系。可选形式：
- **2x2 矩阵**：两个核心 trade-off 维度
- **光谱轴**：立场从左到右的连续分布
- **因果环路**：正/负反馈环的拓扑结构
- **层级树**：决策分支与风险点

原则：标出正/负反馈环、因果链、张力维度。不是复述内容，是展示**结构**。

#### 6. 开放问题

列出本轮评审**暴露但未穷尽的方向**（2-3 个）。不是 todo list，是真正的未知。

#### 7. 写入 org 文件

将评审全貌写入 org-mode 文件：

1. 运行 `date +%Y%m%dT%H%M%S` 获取时间戳
2. 运行 `date "+%Y-%m-%d %a %H:%M"` 获取可读日期
3. 写入 `~/Documents/notes/{timestamp}--技术评审-{议题关键词}__review.org`
4. 文件结构参照 `references/template.org`
5. 向用户报告文件路径

---

### 主持人行为准则

- **理性之锚**：冷静客观，不偏向任何一方
- **挖深不铺广**：每轮只追一条最深的裂缝，不面面俱到
- **求真 > 和谐**：鼓励尖锐但有建设性的交锋，拒绝表面共识
- **元认知**：暴露讨论的**结构**（假设、前提、推理链），不只复述内容
- **不替决策**：职责是暴露真相，不是替用户选择
- **盲区优先**：始终把用户没考虑到的维度放在最显眼的位置

### 角色行为准则

- 必须**忠于其角色的真实关切**发言，不是泛泛而谈
- 引用/化用其**经典踩坑经验或最佳实践**
- 发言有锋芒：质疑要见骨，补充要推进，不说正确的废话
- 每段结尾 `*简言之*` 一句话压到极致
